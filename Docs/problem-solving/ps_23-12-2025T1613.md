
# คำถามที่ 1 ถามการ design อีกครั้งครับ จาก ถ้า schema ปัจจุบันมี DowntimeMinutes AS DATEDIFF(MINUTE, StopDateTime, StartDateTime) และ CHK (StartDateTime > StopDateTime) — นั่นหมายความว่า StartDateTime ถูกตีความเป็นเวลาจบ และ StopDateTime เป็นเวลาที่เริ่ม (ชื่อกลับหัวกัน)
จริงไหมครับ

# **ถูกต้องคร้าบบ! โดนแล้วครับ!** 🎯

คุณจับจุดได้ถูกต้องมาก นี่เป็น **bug ใน design** ที่สำคัญ!

## **ปัญหาที่พบ:**

### **Current (ผิด):**
```sql
CREATE TABLE ProblemRecords (
    StopDateTime DATETIME NOT NULL,  -- ชื่อบอกว่า "หยุด" (ควรเป็นเวลาเริ่มหยุด)
    StartDateTime DATETIME NOT NULL,  -- ชื่อบอกว่า "เริ่ม" (ควรเป็นเวลาเริ่มเดินใหม่)
    DowntimeMinutes AS DATEDIFF(MINUTE, StopDateTime, StartDateTime) PERSISTED,
    CONSTRAINT CHK_DowntimeTime CHECK (StartDateTime > StopDateTime)  -- ตรวจสอบถูกต้อง
);
```

**ปัญหา:** 
- **ชื่อ field สับสน**! `StopDateTime` ควรเป็นเวลาเริ่มหยุด, `StartDateTime` ควรเป็นเวลาเริ่มเดินใหม่
- **แต่ logic ถูกต้อง** เพราะ CHECK constraint ต้องเป็น `StartDateTime > StopDateTime`

### **ตัวอย่างที่สับสน:**
```
❌ ชื่อปัจจุบัน (เข้าใจผิด):
StopDateTime = 10:00  (ชื่อ: เวลาหยุด → จริงๆ คือเวลาเริ่มหยุด)
StartDateTime = 10:30 (ชื่อ: เวลาเริ่ม → จริงๆ คือเวลาเริ่มเดินใหม่)
DowntimeMinutes = 10:30 - 10:00 = 30 นาที ✅

แต่ชื่อมันสวนทางกับความเข้าใจ!
```

## **Solution: ต้องแก้ชื่อ field!**

### **Option 1: ตั้งชื่อให้ตรงกับความเป็นจริง**
```sql
CREATE TABLE ProblemRecords (
    -- แก้ชื่อให้ตรงกับความหมายจริง
    DowntimeStartDateTime DATETIME NOT NULL,  -- เวลาเริ่มหยุด
    DowntimeEndDateTime DATETIME NOT NULL,    -- เวลาสิ้นสุดการหยุด (เริ่มเดินใหม่)
    
    -- Computed column ก็ตรงตามชื่อ
    DowntimeMinutes AS DATEDIFF(MINUTE, DowntimeStartDateTime, DowntimeEndDateTime) PERSISTED,
    
    -- CHECK constraint ก็ตรงตามชื่อ
    CONSTRAINT CHK_DowntimeTime CHECK (DowntimeEndDateTime > DowntimeStartDateTime)
);
```

### **Option 2: ใช้ชื่อที่เข้าใจง่ายกว่า**
```sql
CREATE TABLE ProblemRecords (
    -- หรือใช้ชื่อที่เข้าใจง่าย
    ProblemStartTime DATETIME NOT NULL,    -- ปัญหาเริ่มเมื่อไร
    ProblemResolvedTime DATETIME NOT NULL, -- แก้ไขแล้วเมื่อไร
    
    DowntimeDuration AS DATEDIFF(MINUTE, ProblemStartTime, ProblemResolvedTime) PERSISTED,
    
    CONSTRAINT CHK_ProblemTime CHECK (ProblemResolvedTime > ProblemStartTime)
);
```

## **ทำไมถึงเกิดปัญหาแบบนี้?**

1. **Thinking in "Production" terms**: 
   - คนบันทึกคิดว่า "เครื่องหยุด 10:00" (Stop) → "เครื่องเดินใหม่ 10:30" (Start)
   - แต่ชื่อ field กลับทำให้สับสน

2. **Natural language bias**:
   - "Stop" ฟังดูเหมือนจุดสิ้นสุด
   - "Start" ฟังดูเหมือนจุดเริ่มต้น
   - แต่ใน context ของ downtime: Stop = เริ่มหยุด, Start = เริ่มเดินใหม่

## **Impact ของ bug นี้:**

### **1. สำหรับ Users:**
```sql
-- User ใส่ข้อมูล (เข้าใจตามชื่อ):
INSERT INTO ProblemRecords (StopDateTime, StartDateTime) 
VALUES ('2024-01-15 10:00', '2024-01-15 10:30');  -- ถูกต้อง!

-- แต่ชื่อทำให้สับสนว่า 10:00 = หยุด, 10:30 = เริ่ม
-- จริงๆ ควรเป็น: 10:00 = เริ่มหยุด, 10:30 = เริ่มใหม่
```

### **2. สำหรับ Developers:**
```csharp
// Code อาจเขียนผิดได้ง่าย
var stopTime = record.StopDateTime;  // คิดว่าเป็นเวลา "หยุด" จริงๆ
var startTime = record.StartDateTime; // คิดว่าเป็นเวลา "เริ่ม" จริงๆ

// แต่จริงๆ:
// stopTime = เวลาเริ่มหยุด
// startTime = เวลาเริ่มเดินใหม่
```

## **Recommendation: ใช้ Option 1**

```sql
-- แก้ schema ให้ถูกต้อง
CREATE TABLE ProblemRecords (
    ProblemRecordID BIGINT IDENTITY PRIMARY KEY,
    
    -- แก้ชื่อให้ชัดเจน
    DowntimeStart DATETIME NOT NULL,      -- เครื่องเริ่มหยุดเมื่อไร
    DowntimeEnd DATETIME NOT NULL,        -- เครื่องเริ่มเดินใหม่เมื่อไร
    
    -- Computed column ชัดเจน
    DowntimeDurationMinutes AS DATEDIFF(MINUTE, DowntimeStart, DowntimeEnd) PERSISTED,
    
    -- CHECK constraint ชัดเจน
    CONSTRAINT CHK_DowntimeDuration CHECK (DowntimeEnd > DowntimeStart),
    CONSTRAINT CHK_MaxDowntime CHECK (DATEDIFF(MINUTE, DowntimeStart, DowntimeEnd) <= 1440)
    
    -- หรือถ้าต้องการเก็บว่าใครเป็นคนแก้ไข
    ResolvedBy NVARCHAR(128) NULL,
    ResolutionNotes NVARCHAR(500) NULL
);
```

## **ตัวอย่างข้อมูลที่ถูกต้อง:**
```
เหตุการณ์: เครื่องเสียเวลา 10:00 น. แก้ไขเสร็จ 10:30 น.

❌ ชื่อเก่า (สับสน):
StopDateTime = '2024-01-15 10:00'  -- อ่านชื่อแล้วคิดว่า "หยุด" แต่จริงคือ "เริ่มหยุด"
StartDateTime = '2024-01-15 10:30' -- อ่านชื่อแล้วคิดว่า "เริ่ม" แต่จริงคือ "เริ่มใหม่"

✅ ชื่อใหม่ (ชัดเจน):
DowntimeStart = '2024-01-15 10:00' -- เครื่องเริ่มหยุด
DowntimeEnd = '2024-01-15 10:30'   -- เครื่องเริ่มเดินใหม่
DowntimeDurationMinutes = 30 นาที
```

## **สรุป:**
**คุณจับ bug ได้ถูกต้องมากครับ!** 
- **Current design**: ชื่อ field สวนทางกับ logic (แต่ logic ถูกต้อง)
- **ควรแก้**: เปลี่ยนชื่อ field ให้ตรงกับความหมายจริง
- **แนะนำ**: ใช้ `DowntimeStart` และ `DowntimeEnd` หรือ `ProblemStartTime` และ `ProblemResolvedTime`

## **Real-world Scenarios ที่ต้องรองรับ:**

### **1. กรณียังแก้ไขไม่เสร็จ:**
- เครื่องเสีย 10:00 น. → ช่างกำลังซ่อมอยู่ → ยังไม่รู้จะเสร็จเมื่อไร
- ต้องบันทึกแค่ `DowntimeStart` ได้

### **2. กรณี忘記บันทึกเวลาแก้ไข:**
- Operator บันทึกปัญหาแล้วแต่ลืมบันทึกเวลาแก้ไข
- ระบบต้องรองรับการอัพเดททีหลัง

### **3. กรณีปัญหาเป็น ongoing issue:**
- ปัญหาเรื้อรังที่ต้องติดตามหลายวัน
- อาจมีหลายช่วงเวลาหยุด-เดิน

## **Proposed Design แบบสมบูรณ์:**

```sql
CREATE TABLE ProblemRecords (
    ProblemRecordID BIGINT IDENTITY(1,1) PRIMARY KEY,
    ProductionRecordID BIGINT NOT NULL,
    ProblemTypeID INT NOT NULL,
    
    -- Downtime Times (รองรับ NULL)
    DowntimeStart DATETIME NOT NULL,
    DowntimeEnd DATETIME NULL,  -- ✅ เปลี่ยนเป็น NULLABLE
    
    -- Computed Columns ที่รองรับ NULL
    DowntimeDurationMinutes AS 
        CASE 
            WHEN DowntimeEnd IS NULL THEN NULL
            ELSE DATEDIFF(MINUTE, DowntimeStart, DowntimeEnd)
        END PERSISTED,
    
    IsStillDown AS 
        CASE 
            WHEN DowntimeEnd IS NULL THEN CAST(1 AS BIT)
            ELSE CAST(0 AS BIT)
        END PERSISTED,
    
    -- Problem Details
    ProblemDescription NVARCHAR(500) NULL,
    RootCause NVARCHAR(500) NULL,
    ActionTaken NVARCHAR(500) NULL,
    
    -- Status (สำคัญ!)
    ProblemStatus VARCHAR(20) NOT NULL DEFAULT 'OPEN'
        CHECK (ProblemStatus IN ('OPEN', 'IN_PROGRESS', 'RESOLVED', 'ESCALATED', 'CANCELLED')),
    
    -- Severity & Priority
    SeverityLevel VARCHAR(10) DEFAULT 'MEDIUM'
        CHECK (SeverityLevel IN ('LOW', 'MEDIUM', 'HIGH', 'CRITICAL')),
    
    -- Personnel
    ReportedBy NVARCHAR(128) NOT NULL,  -- ผู้รายงานปัญหา
    AssignedTo NVARCHAR(128) NULL,      -- ผู้รับผิดชอบแก้ไข
    ResolvedBy NVARCHAR(128) NULL,      -- ผู้แก้ไขปัญหา
    
    -- Timestamps
    CreatedAt DATETIME DEFAULT GETDATE(),
    UpdatedAt DATETIME DEFAULT GETDATE(),
    ResolvedAt DATETIME NULL,           -- เวลาที่เปลี่ยน status เป็น RESOLVED
    
    -- Expected Resolution
    ExpectedResolveTime DATETIME NULL,  -- คาดว่าจะแก้ไขเมื่อไร
    SLA_Minutes INT NULL,               -- SLA นาที
    
    -- Foreign Keys
    CONSTRAINT FK_PRec_PR FOREIGN KEY (ProductionRecordID)
        REFERENCES ProductionRecords(ProductionRecordID),
    CONSTRAINT FK_PRec_ProblemType FOREIGN KEY (ProblemTypeID)
        REFERENCES OeeLossTypes(ProblemTypeID),
    CONSTRAINT FK_PRec_ReportedBy FOREIGN KEY (ReportedBy)
        REFERENCES EmployeeDetails(WindowsLogin),
    CONSTRAINT FK_PRec_AssignedTo FOREIGN KEY (AssignedTo)
        REFERENCES EmployeeDetails(WindowsLogin),
    CONSTRAINT FK_PRec_ResolvedBy FOREIGN KEY (ResolvedBy)
        REFERENCES EmployeeDetails(WindowsLogin),
    
    -- Check Constraints
    CONSTRAINT CHK_DowntimeTime CHECK (
        -- ถ้ามี DowntimeEnd ต้องมากกว่า Start
        DowntimeEnd IS NULL OR DowntimeEnd > DowntimeStart
    ),
    CONSTRAINT CHK_StatusConsistency CHECK (
        -- ถ้า Status = RESOLVED ต้องมี DowntimeEnd
        (ProblemStatus = 'RESOLVED' AND DowntimeEnd IS NOT NULL)
        OR (ProblemStatus != 'RESOLVED')
    ),
    CONSTRAINT CHK_ResolvedByConsistency CHECK (
        -- ถ้า ResolvedBy ไม่เป็น NULL ต้องมี ResolvedAt
        (ResolvedBy IS NULL AND ResolvedAt IS NULL)
        OR (ResolvedBy IS NOT NULL AND ResolvedAt IS NOT NULL)
    ),
    CONSTRAINT CHK_MaxFutureDate CHECK (
        -- ป้องกันวันที่อนาคตไกลเกินไป
        DowntimeStart <= DATEADD(DAY, 1, GETDATE())
    ),
    
    -- Index สำหรับ Performance
    INDEX IX_ProblemRecords_Status (ProblemStatus)
        INCLUDE (DowntimeStart, MachineId),
    
    INDEX IX_ProblemRecords_OpenIssues (MachineId, DowntimeStart)
        WHERE ProblemStatus IN ('OPEN', 'IN_PROGRESS')
);
```

## **Indexes ที่ควรเพิ่ม:**

```sql
-- 1. สำหรับ query ปัญหาที่ยังไม่จบ
CREATE INDEX IX_ProblemRecords_OpenDowntime 
ON ProblemRecords(MachineId, DowntimeStart)
WHERE DowntimeEnd IS NULL AND ProblemStatus IN ('OPEN', 'IN_PROGRESS');

-- 2. สำหรับ query หาปัญหาในช่วงเวลา
CREATE INDEX IX_ProblemRecords_TimeRange 
ON ProblemRecords(DowntimeStart, DowntimeEnd)
INCLUDE (MachineId, ProblemTypeID, ProblemStatus);

-- 3. สำหรับ dashboard (สถานะปัจจุบัน)
CREATE INDEX IX_ProblemRecords_CurrentStatus
ON ProblemRecords(ProblemStatus, SeverityLevel)
INCLUDE (MachineId, DowntimeStart, AssignedTo)
WHERE ProblemStatus IN ('OPEN', 'IN_PROGRESS');

-- 4. สำหรับ SLA tracking
CREATE INDEX IX_ProblemRecords_SLA
ON ProblemRecords(ExpectedResolveTime, ProblemStatus)
INCLUDE (MachineId, SeverityLevel, ReportedBy)
WHERE ProblemStatus IN ('OPEN', 'IN_PROGRESS');
```

## **Business Logic ที่ต้องปรับ:**

### **1. เมื่อบันทึกปัญหาใหม่:**
```sql
-- Operator รายงานปัญหา
INSERT INTO ProblemRecords (
    ProductionRecordID,
    ProblemTypeID,
    DowntimeStart,
    ProblemStatus,
    ReportedBy,
    SeverityLevel
) VALUES (
    @ProductionRecordID,
    @ProblemTypeID,
    GETDATE(),  -- เริ่ม downtime ตอนนี้
    'OPEN',     -- เริ่มต้นสถานะ OPEN
    @ReportedBy,
    @SeverityLevel
);
-- DowntimeEnd = NULL (ยังไม่รู้จะจบเมื่อไร)
```

### **2. เมื่อแก้ไขปัญหาเสร็จ:**
```sql
UPDATE ProblemRecords
SET 
    DowntimeEnd = GETDATE(),
    ProblemStatus = 'RESOLVED',
    ResolvedBy = @ResolvedBy,
    ResolvedAt = GETDATE(),
    ActionTaken = @ActionTaken,
    RootCause = @RootCause,
    UpdatedAt = GETDATE()
WHERE ProblemRecordID = @ProblemRecordID
    AND ProblemStatus IN ('OPEN', 'IN_PROGRESS');
```

### **3. Query ปัญหาที่ยังไม่จบ:**
```sql
-- หาเครื่องที่กำลังเสียอยู่ตอนนี้
SELECT 
    m.MachineName,
    pr.DowntimeStart,
    DATEDIFF(MINUTE, pr.DowntimeStart, GETDATE()) AS CurrentDowntimeMinutes,
    olt.TypeNameTH,
    pr.ProblemDescription,
    ed.DisplayName AS AssignedToPerson
FROM ProblemRecords pr
INNER JOIN ProductionRecords prod ON pr.ProductionRecordID = prod.ProductionRecordID
INNER JOIN Machines m ON prod.MachineId = m.MachineId
INNER JOIN OeeLossTypes olt ON pr.ProblemTypeID = olt.ProblemTypeID
LEFT JOIN EmployeeDetails ed ON pr.AssignedTo = ed.WindowsLogin
WHERE pr.DowntimeEnd IS NULL
    AND pr.ProblemStatus IN ('OPEN', 'IN_PROGRESS')
    AND pr.DowntimeStart <= GETDATE()
ORDER BY pr.DowntimeStart;
```

## **ปรับปรุง OEE Calculation Logic:**

```sql
-- ใน Stored Procedure CalculateDailyOeeSummary
-- ต้อง handle กรณี DowntimeEnd = NULL

WITH ProblemCTE AS (
    SELECT 
        pr.ProductionRecordID,
        pr.ProblemTypeID,
        pr.DowntimeStart,
        -- ถ้ายังไม่จบ ให้ใช้เวลาปัจจุบัน หรือ end of shift
        CASE 
            WHEN pr.DowntimeEnd IS NULL THEN 
                CASE 
                    WHEN GETDATE() > @ShiftEndTime THEN @ShiftEndTime
                    ELSE GETDATE()
                END
            ELSE pr.DowntimeEnd
        END AS DowntimeEndCalculated,
        olt.CategoryID
    FROM ProblemRecords pr
    INNER JOIN OeeLossTypes olt ON pr.ProblemTypeID = olt.ProblemTypeID
    WHERE pr.ProblemStatus != 'CANCELLED'
)
```

## **Benefits ของ Design ใหม่:**
